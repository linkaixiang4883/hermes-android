> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** 输入区用量条右侧加压缩按钮，点后经 WS `slash.exec` 触发服务端 `/compress`，成功后刷新用量条并重拉聊天记录。

## 数据流

```text
tap 压缩按钮（启用条件：!_sending && !_streaming 且有 WS）
  └─ 确认框（标题+说明不可逆，确认/取消）
  └─ 按钮转 loading → slashExec('/compress', sessionId)
        ├─ 成功 {output} → SnackBar 显示结果摘要 → _refreshContextUsage() + _fetchMessages()
        ├─ 4018/5030 → SnackBar 显示服务端原话（橙条）
        └─ busy（理论上被禁用态挡住，漏网则服务端回 busy 文案）→ SnackBar 提示先停止当前回复
```

## 显示文案（定死）

- 新增 ARB key（616→约 622），带参 key 加 `@key` placeholders：
  - `compressTitle`：`压缩上下文` / `Compress context`（确认框标题）
  - `compressConfirmMessage`：`将历史压缩为摘要，此操作不可撤销。继续吗？` / `Summarize history into a compact form. This cannot be undone. Continue?`
  - `compressConfirm`：`压缩` / `Compress`；`cancel` 复用既有 key，不新增
  - `compressRunning`：`压缩中…` / `Compressing…`（按钮 loading 态 tooltip/Semantics）
  - `compressDone`：`压缩完成` / `Compression done`（SnackBar 前缀，后接 output 摘要）
  - `compressFailed(error:String)`：`压缩失败：{error}` / `Compression failed: {error}`

## 调研结论归档（2026-09-06，真机实测，本单暂停）

- 超时根因：slash.exec 等待超时 45s（`_SLASH_WORKER_TIMEOUT_S`，`server.py:103`），大压缩必超时→5030→App 橙条（4 秒易错过）→圈圈消失按钮复位，但服务端继续压。F1a（调大 env）因依赖用户配环境已否决。
- 二次点击：App 不拦；服务端有 `compression_locks`/竞态恢复，数据大概率不坏但白烧 token；且 busy 拒绝走成功包 `warning` 字段（App 不读→误报成功）。
- 轮换：压缩后 session id 可能变（实测 `...015501`→`...030447`）；旧 id 发消息服务端 `_adopt_if_parent_rotated` 自动认领，大概率不炸；但 App 超时路径未刷新→显示旧历史+旧用量，必须手动回列表刷新重进。
- 完成通知：`status_callback("compacted")` 通道调用方收不到；`sessions.changed` 广播理论可行（state.db mtime，App 零监听），但新增上游事件耦合、维护成本否决（待议）。
- 用户决策：Q1=A1 确认框要；Q2=A2 直接实现真机验收；测试会话 `20260906_015501_982158` 备用；B 半自动（超时转提示条+手动刷新）vs A 全自动待定。
- 处置：复杂度超支，代码回退到用量版（`25c7ceb`），本单暂停；重启条件：接受 B 方案或全自动方案。
